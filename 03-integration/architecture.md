# Интеграция Bitrix24, Moodle и личного кабинета студента

## 1. Источник истины (System of Record)

### Bitrix24

Bitrix24 является главным источником данных о пользователе как о клиенте/абитуриенте:

- ФИО;
- контакты;
- статус абитуриента;
- статус "студент";
- учебная группа;
- изменения персональных данных.

### Moodle

Moodle отвечает за учебный процесс:

- курсы;
- задания;
- оценки;
- материалы;
- посещение занятий.

### Личный кабинет студента

Личный кабинет является пользовательским интерфейсом для студента:

- профиль;
- отображение учебной информации;
- доступ к сервисам.

Учебные данные не редактируются напрямую в личном кабинете, а приходят из систем-источников.

## 2. Передаваемые данные

| Откуда | Куда | Данные |
|---|---|---|
| Bitrix24 | Moodle | создание пользователя, ФИО, email, учебная группа, идентификатор студента |
| Bitrix24 | Личный кабинет | профиль студента, статус, группа |
| Moodle | Личный кабинет | курсы, оценки, задания, расписание |
| Личный кабинет | Moodle | запросы на получение учебной информации |

## 3. Способ интеграции

Для обмена данными используется REST API через отдельный интеграционный сервис.

Интеграционный сервис отвечает за:
- преобразование форматов данных;
- повторную отправку при ошибках;
- журналирование операций;
- контроль дублей.

Прямые связи Bitrix24 → Moodle → Личный кабинет не используются, чтобы уменьшить связанность систем.

## 4. Обработка недоступности Moodle

Если Moodle недоступен 6 часов:

1. Bitrix24 не ждёт ответ Moodle синхронно.
2. Событие о переводе абитуриента в статус "студент" сохраняется в очередь.
3. Интеграционный сервис периодически повторяет отправку.
4. После восстановления Moodle данные отправляются автоматически.

Используется механизм retry с ограничением количества попыток.

Все операции записываются в журнал интеграции:
- время;
- тип операции;
- ID студента;
- статус выполнения;
- текст ошибки.

## 5. Защита от дублей

Для каждого студента используется внешний идентификатор.

Например:

Bitrix24:
student_id = 12345

При создании пользователя в Moodle сохраняется этот же внешний ID.

Перед созданием новой записи выполняется проверка:

- если внешний ID уже существует — выполняется обновление;
- если нет — создаётся новая запись.

Это обеспечивает идемпотентность операций.

## 6. Допущения и недостающая информация

### Допущения

1. Bitrix24 является владельцем данных о студенте и его статусе.
2. Moodle предоставляет API для создания пользователей и получения учебных данных.
3. Личный кабинет имеет собственное API для получения данных.
4. Все системы могут идентифицировать студента через единый внешний ID.
5. Интеграционный сервис имеет доступ к API всех систем.

### Недостающая информация

Для точного проектирования нужны:

- документация API Bitrix24;
- возможности API Moodle;
- требования к частоте синхронизации;
- объём истории изменений;
- требования по безопасности и хранению персональных данных;
- требования по отказоустойчивости.
